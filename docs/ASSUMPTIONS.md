# Implementation decisions

1. The user's `frontend/` and `backend/` names take precedence over the PDF's `apps/web` and `apps/api`. The previous prototype is preserved in `docs/initial-prototype/src/`.
2. The latest request enumerates all ten functional modules. Their code is now delivered, plus the originally requested profile. Phased acceptance remains pending live verification; it is not silently marked complete.
3. `.env` files are ignored. Project URL and publishable key are configured locally; server keys stay in backend only. A publishable key can use the existing `SUPABASE_ANON_KEY` variable name. A database password is not a server API key or CLI access token.
4. React 18, React Router 6, strict TypeScript, TanStack Query, React Hook Form/Zod, Tailwind and shadcn-compatible Radix primitives remain the declared stack. Vite's built-in automatic JSX transform is used. Cached frontend Router/Query/icon versions differ from pins; a clean install/lockfile refresh is still required.
5. There is no signup route. A service-key-protected operator script bootstraps only the first admin; subsequent accounts use authenticated admin actions. Temporary passwords always force a change. Only a real Auth password-hash change clears that gate.
6. Sensitive workflow writes use security-definer SQL RPCs with fixed search paths and caller/role/course checks. Caller-JWT reads retain RLS. The API does not use service privileges for student or teacher coursework, grading, quiz, chat or complaint operations.
7. All tables include created_at and mutable tables include updated_at. The extra notifications table supplies private complaint status notices. Marks stay derived. All reporting/member RPCs explicitly enforce scope.
8. Profile name is editable; email, role and roll number remain institution-managed. Password/security controls and real course/submission/quiz/marks metrics are implemented. No unverifiable study-hour or completion-rate metrics are invented.
9. Course archive hides it from students/teachers; admins retain visibility. CSV enrollment accepts JSON containing CSV text to enable preview/confirmation, up to 100 email rows per batch. Picker lists display at most 100 matches; larger batches can use CSV/API pagination.
10. Upload limits use 25 MiB and complaint attachments 10 MiB. Magic bytes, extension and MIME are checked server-side. Paths use course/user/UUID-filename (or user/UUID-filename for complaints) to independently enforce ownership. Metadata and Storage cannot commit atomically; owner-scoped orphan cleanup is an operational follow-up.
11. Quiz retakes and chat attachments are excluded. Marks release immediately on grade save. Multi-select grading compares exact sets. Expired quiz submissions are rejected after the ten-second grace. Unsaved quiz answers are held in memory, not persisted across reload.
12. Chat is text-only and HTML is rendered as text. Admins read/moderate but do not send, following the permission table. History uses a before timestamp; ties at page boundaries need a compound cursor for perfect ordering under simultaneous inserts.
13. Complaint flow is open -> in_review -> resolved/rejected with a response for terminal states. Private notifications are inserted transactionally. Follow-up comments are omitted as an optional extension.
14. Recovery uses a one-time token_hash through the API; hosted recovery email templates must use the included template. Reset/change revokes all sessions; session existence is checked by the API and RLS. Existing signed Storage URLs can survive until their expiry.
15. The original PDF, extracted text and local seed are references/fixtures, not a deployment instruction. The local seed intentionally uses public demo credentials and must not run on hosted/production databases.
16. Rate-limit state is local/in-process. Multi-replica deployment needs shared state and explicit trusted proxy settings. Supabase SMTP, real Realtime latency, database behavior and browser accessibility remain unverified until deployment gates pass.
